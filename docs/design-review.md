# Design iteration record

## Target

The visual target is the illustrated cyan/red physical playmat in [NSG's example game](https://www.youtube.com/watch?v=xtI0-j0utLo). Card reading should feel closer to established digital card games: prominent hand, hover/focus magnification, pinned inspection, and clear legal actions. This is inspired by the reference, not an exact recreation or use of the video's artwork.

The workflow applied the useful part of [Theo's iteration discussion](https://www.youtube.com/watch?v=xq0eB8vxeqk): implement, render, critique against concrete references, change the identified defects, and compare again. An independent reviewer examined the references, source/DOM measurements, and then actual screenshots. No arbitrary numeric target or invented quality score was used.

## Iterations

1. **Initial static study:** generic dark schematic mats, small cards, large sidebar, and staged interaction. Reviewer identified the missing illustrated mat, weak card presence, and the need to test actual dense games.
2. **Playable first pass:** original illustrated playmat, narrow legal-decision rail, real worker-backed rules and AI, card hover and inspection. [Screenshot](screenshots/pass-1.png). Reviewer found that cards remained too small relative to empty mat space; R&D count placement was inconsistent.
3. **Card reading and state clarity:** enlarged hands/rig/server cards; 600×839 inspection originals; current strength, complete counters, unrezzed badges; individual encountered-ICE highlight; optional choices and multiple-card selections preserved. Width-based hand overlap and mobile Heap access corrected. Pinned card also presents selectable rules text at normal UI font sizes.
4. **Full-game density:** both sides played through actual UI to terminal results. A later position pushed the hand beyond the desktop viewport. Fixed grid/flex minimum sizing, kept the hand anchored, made each crowded play area independently scrollable, allowed horizontal rig/server scrolling, and moved scored agendas into an inspectable score total. [Dense board](screenshots/dense-board.png).
5. **Final encounter pass:** available breaker action receives primary emphasis; current ice and subroutines remain together in the rail; crowded play areas expose a scroll control. [Encounter](screenshots/encounter.png). The independent reviewer found no blocking readability defect in the supplied desktop dense/encounter states. Remaining cinematic depth and elaborate animation are future polish, not claims made by this release.

## Scope

This first release has two legal System Gateway presets and the upstream heuristic opponents. It does not implement recent expansions, a deck editor, online multiplayer, or learned policies. The all-Gateway card registry is retained for future deck work. Tests cover important rule paths and complete games; they are not exhaustive verification of every card interaction.

## Luminal extra-click turn correction — 2026-11-05 local

The user's `netrunner-replay-e5041c11.json` reproduces a rules bug on Corp turn 7: Regolith activation, advancement and Seamless Launch exhaust the Corp's clicks; scoring Luminal then grants three clicks, but the game enters discard and starts the Runner turn with those clicks still showing. The helper correctly flagged the suspicious sequence, although its suggestion that the Corp might voluntarily end early was incorrect. Rule 5.4.2 requires players to continue taking actions while clicks remain unless a card directly ends the action phase. Luminal forbids further scoring, not further actions.

The adapter incorrectly applied a one-time guard to every `PreEnumerate` hook. Upstream calls these hooks whenever choices are regenerated; combined Corp response/action windows use them to recalculate the next phase. When the zero-click window was revisited after scoring effects, its stored discard destination was never recalculated. The adapter now follows that upstream contract, leaving one-time guarding to the hooks that implement it themselves. The vendored source is unchanged.

The original export is retained as `tests/fixtures/luminal-extra-clicks-replay.json`. Restoring it now spends all three bonus clicks before the Runner starts: two Regolith activations, then an install. The live worker streams those actions into playback. Regression coverage also scores Luminal as a human Corp with zero clicks, resolves its trigger, spends the three granted clicks through normal choices, and confirms that another ready agenda cannot be scored that turn. The helper's supplied rule notes now explicitly rule out voluntarily ending early.

The correction necessarily changes later positions in games that already continued after this bug. The historical interaction Chrome fixture's first 90 decisions replay, then its next recorded decision has a stale version because the corrected Corp performed its three actions. That suffix is retained as historical evidence and tested for rejection without state mutation; it is not rewritten or claimed as a new browser playthrough. The user's export ends at the affected scoring turn and restores successfully in full. Full `npm test` passes. ## Chiriboga frontend and timing audit — 2026-11-06 local

This audit compares the pinned original source (`77c80b1`) with the adapter, worker protocol and frontend. It follows the native `Main → EnumeratePhase → ExecuteChosen → Execute → MakeChoice → ResolveChoice` path, rather than assuming unchanged card scripts guarantee unchanged behavior. ### Newly reproduced issues and fixes

**Phase-handler receiver mismatch.** The original `runSubroutines.Resolve.trigger` calls its sibling `this.n()` when a subroutine moves directly to the pass-ice/unsuccessful phase. Our adapter bound `this` to the phase object, which has no `n` method. A focused phase-changing subroutine fixture reproduced `this.n is not a function` in that existing upstream cleanup branch. Resolution and cancellation now preserve the original method receivers. This branch is not routinely reached by the fixed Gateway presets, so this is a confirmed integration contract failure, not a claim that every ordinary end-the-run subroutine was broken.

**Replay batch boundary.** Restoration called `NR.advance()` once after each saved choice. If progression exceeded its batch budget, the next saved choice could be submitted before the engine reached the next real human decision. The old outer worker loop ran too late to repair that. The worker now drains to a genuine decision during initial setup, between replay choices, and after live choices. `NR.needsAdvance()` distinguishes AI/forced-pass windows from actual human decisions, including a forced human pass at the batch boundary. Tests run the real engine with a one-resolution batch and require exact equality with an unrestricted replay. This reproduces the scheduling failure without inventing a large or malformed board.

**Accepted-action rollback on later error.** The frontend left its action marked pending after the worker's post-resolution resource message. If the AI subsequently failed, the error handler removed that already-accepted action from the saved trace; a later Undo then removed the preceding action. The acknowledgement now clears pending status immediately. The worker also reports acceptance if building the first observation itself fails. Rejected actions are rolled back once; accepted actions are retained. Error positions have no usable decision, preventing a board click from submitting stale actions while the sidebar reports failure.

**Unrepresented viewing windows.** A deck card temporarily turned faceup by `Reveal` was absent from the DTO's hand/board/resolving/access fields. The original displayed a zoomed card, while our UI could show only a Continue prompt and a title. Reveal/expose phases now carry one explicit, visibility-checked card reference. The table displays that card with a viewing heading, and the helper receives its text. The reference expires on Continue. Mandatory viewing does not auto-pass, and a later facedown deck card is excluded again. Gateway's Malapert Data Vault is an example of the relevant deck-reveal pattern; it is outside the two current preset decks, so this was found through a focused engine fixture rather than an observed user match.

**Stale replay recovery.** The former recovery advice required repeatedly undoing choices from an incompatible suffix. The worker now reports the count of successfully restored decisions. The UI offers Export original & recover: it first exports the full trace, then starts a fresh worker with only the compatible prefix. It does not silently rewrite later decisions. The old Luminal continuation is covered explicitly: 35 recorded choices restore, the next pre-fix decision is rejected, and the retained prefix resumes with the corrected bonus-click sequence. Restoring a changed-rules game does not preserve the incompatible later turns.

### Remaining constraints and intentional gaps

- Native `ExecuteChosen` dispatches `automaticOnAnyChange`; our adapter does not. No handler for that callback is registered in the pinned Gateway set, so there is no current Gateway effect to reproduce. This is a concrete compatibility gap to close and test before importing sets that use it, rather than an asserted current-match bug.
- Cost labels are a presentation projection, with specific handling for basic actions, selected economy abilities, bioroids, installs and access trashing. The subsequent [encounter interaction pass](playtesting/encounter-actions.md) adds payment-tested quotes for all seven Gateway breakers and Botulus/Leech. This remains explicit support for the pinned set, not a generic cost engine for future cards.
- The original tutorials, graphical drag/drop workflow, narration, deck configuration, and automatic-continue controls are not equivalent features in this frontend. The playable scope remains the two Gateway presets.
- The AI still runs with the original shared-global implementation. The public DTO/helper boundary is filtered, but this audit is not an independent information-access audit or strength benchmark of both bots.
- This pass used source inspection, the actual native enumerator, isolated engine/worker execution and a VM harness running the real frontend message/click handlers. It did not perform a new native Chrome visual pass. Previously captured geometry tests remain historical captures, not fresh screenshots of these changes.
